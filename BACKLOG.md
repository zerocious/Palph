# Backlog — сырые идеи

Этот файл — для **необработанных идей**: то, что ещё не оценено, не размечено по приоритетам и не готово к спринту. Когда идея созревает (есть критерий готовности, понятна цена, выбран приоритет) — переезжает в [TODO.md](TODO.md).

Отличие от секции «Бэклог» в TODO.md:
- **TODO.md → Бэклог** — отложенные задачи с критерием готовности и приоритетом (Must/Should/Could/Won't), просто не в текущем спринте.
- **BACKLOG.md (этот файл)** — идеи без оценки. Сюда сбрасываем мысли, чтобы не потерять, не загромождая TODO.md.

Формат записи (свободный, но желательно):

```
## Заголовок (дата захвата)
**Идея**: суть в 1–2 предложениях
**Зачем**: ценность для пользователя/продукта
**Подход (черновой)**: как могло бы быть реализовано
**Риски**: что может пойти не так
**Стоимость**: примерный объём (код / контент / арт)
**Решение**: defer / yes / no / нужно больше данных
```

## Контекстуализированные («applied») задачи по математике (2026-05-17)

**Идея**: к режиму задач (#14 в TODO.md) добавить задачи-сценарии в формате «ты инженер/менеджер/программист, реши проблему», чтобы математика воспринималась как инструмент, а не самоцель.

**Зачем**:
- Мотивация — «зачем мне это» главная причина дропа в STEM.
- Transfer (перенос знаний): студенты, тренировавшиеся только на абстракции, часто не могут применить ту же математику в новом контексте.
- Дифференциация: Anki / Quizlet / учебники дают абстрактные задачи; applied-ниша свободна.

**Подход (черновой)**:
- **НЕ отдельный режим.** Поле `flavor: "textbook" | "applied"` в JSON задачи (#14).
- Внутри темы: первые 2–3 задачи — чистая математика (закрепить навык), потом applied (показать зачем). Khan Academy делает так же: skill → application.
- Визуальная маркировка: 📐 textbook, 💼 applied.

**Риски**:
- Контент-стоимость ×3–5: хорошая applied-задача требует правдоподобного сценария + проверки что математика реально та же. Плохая хуже абстрактной — добавляет шум.
- Cognitive Load Theory (Sweller): новичкам контекст **мешает**, пока навык не автоматизирован. Важен порядок (abstract → applied), не «два режима на выбор».
- Telegram плохо подходит для длинных сценариев (scroll fatigue) — условия держать короткими.
- Самописные applied-задачи легко скатываются в cringe. Лучше брать у профи в нише или LLM-генерация с человеческим ревью.

**Стоимость**:
- Код: ~0 поверх #14 (поле в JSON + иконка).
- Контент: высокая — нужны интервью с профессионалами или LLM + ревью.
- Арт: 0 (картинка задачи уже в #14).

**Решение**: **defer до v0.8**. Сначала запустить #14 в текущем виде, увидеть как реальные пользователи проходят задачи. Возможно, абстрактных хватит и applied-трек не нужен. Если данные покажут низкий engagement по математике — вернуться к идее.

## Username-search для /friends ✅ shipped 2026-05-19

Поднято с defer на ship в той же сессии (после Phase 4 friends).
Реализация:
- `users.username TEXT` колонка + migration.
- `UsernameSyncMiddleware` обновляет username на каждом Message/CallbackQuery (FK-safe; failures swallow'ятся).
- `UserRepository.refresh_username` + `find_user_id_by_username` (case-insensitive `COLLATE NOCASE`).
- `services.parse_friend_query` — pure parser, принимает `@alice` / `alice` / `12345` / `-12345`.
- `friend_add_process` сначала пытается username path → fallback на numeric.
- 22 теста: parser variants + repo round-trips + case-insensitive lookup.

Privacy-toggle (opt-out из username discovery) НЕ добавлен — спор был о том, нужен ли отдельный privacy-канал кроме `hidden_from_leaderboards`. Defer до user-feedback'а.

Re-validation на stale username (A удалил @foo, B взял) тоже НЕ реализована — Telegram API через `bot.get_chat(username)` мог бы валидировать, но это добавляет round-trip и API rate-limit. v1 принимает stale-cache риск; если станет реальной проблемой — поднять в backlog.

## Friend invite-link через deep links ✅ shipped 2026-05-19

Поднято с defer на ship сразу после username-search (одна сессия).
Финальная реализация:
- `friend_invite_tokens` (token PK, from_user_id, created_at, expires_at).
  Многоразовый токен с 30-day TTL.
- `FriendRepository.create_invite_token` (16-char token из `secrets.token_urlsafe`),
  `find_invite_token` (отсекает истёкшие), `accept_invite` (atomic под
  `db.lock`, skip pending state — deep-link клик это уже согласие обеих сторон).
- `/share_friend` команда → создаёт токен, формирует `t.me/<bot_username>?start=friend_<token>`,
  шлёт пользователю.
- `/start friend_<token>` deep-link → `_process_friend_invite_link`:
  резолвит токен, accept_invite, уведомляет invitee + creator.
- 17 тестов: token uniqueness/expiry, find resolution, accept happy/self/already,
  multi-use, pending request cleanup, end-to-end flow.

Решение про **прямую дружбу вместо pending request**: deep-link клик
семантически = двустороннее consent (creator shared, invitee clicked).
Конвертация в pending-state добавила бы ненужный шаг для viral-кейса.

Рисков, которые НЕ адресованы в v1:
- Спам-vector: Alice расшарила в публичный группу → 100 человек кликнули → Alice
  получила 100 друзей. Mitigation (rate limit per-day) не добавили — для
  маленького русскоязычного uni-бота это нереалистичный сценарий. Если
  жалобы появятся — поднять в backlog.
- Per-token usage cap: токен можно использовать неограниченно. Тот же сценарий
  выше. Mitigation = добавить `max_uses` колонку и декремент при accept.

## Индивидуальный учебный план на основе диагностики и прогресса (2026-05-18)

**Идея**: при первом входе в предмет — короткий входной тест (5-10 смешанных вопросов: теория + задачи), на основе которого + накопленных данных прогресса бот собирает **персональный план дня**: «сегодня изучи это, повтори это, попробуй эту задачу». План адаптируется по мере того, как пользователь учится.

**Зачем**:
- Сокращает «когнитивный налог»: не «выбери что учить», а «вот твоя порция на сегодня»
- Адаптация под уровень: новичок видит базовые карточки, продвинутый — сложные задачи. Меньше скуки и фрустрации.
- Дифференциация: статичные Anki / Quizlet дают одно и то же всем — adaptive plan действительно «знает» пользователя.
- Использует существующую инфру v0.7: `mcq_progress`, `task_progress`, `flashcard_progress`, `quiz_progress` уже хранят per-item состояние — нужна только модель «навыков»/«тем» сверху.

**Подход (черновой)**:
- **Diagnostic test** (5-10 заданий): смешанные режимы (MCQ + open + 1 задача), покрывают основные концепты предмета. Запускается при первом входе в предмет (опционально skip-button «уже знаю / просто учусь»).
- **Skill map**: для каждой темы внутри предмета — оценка пользователя (например 0..3: «не знаю», «знаю слабо», «знаю», «свободно»). Сначала из diagnostic, потом обновляется на каждом ответе.
- **Plan generator** (raw): ежедневный список из N items (8-12), составленный по правилам приоритетов:
  1. Overdue review (SRS) — карточки и термины с `next_review ≤ today`
  2. Зоны слабости (skill < 2 по теме)
  3. Прогрессия: после освоенной темы — следующая по логике предмета
  4. Mix режимов: не больше 5 одинаковых подряд (избегать усталости)
- **UI**: новая кнопка «📋 Сегодняшний план» в subject-меню → нумерованный список с прогрессом «3/10 готово». По завершении плана — баннер «🎉 День сделан».
- **Контент-тегирование**: items в `flashcards.txt`/`mcq.txt`/`tasks/*.json` получают опциональный `topic: "string"` (или массив тем) — связывает их со skill map.

**Риски**:
- **Качество diagnostic test определяет всё**. Плохой тест → плохая модель → плохой план → пользователь злится. Нужно реальное профильное знание предмета чтобы составить дискриминирующий тест.
- **Тегирование контента — ручной труд**. Без тем нет skill map. Либо автор предмета вручную раскидывает термины по темам, либо LLM-классификация (но это шум).
- **Cold start**: первые 1-2 сессии у пользователя нет статистики → план будет шаблонным. Тут спасает diagnostic test.
- **Opacity problem**: «почему бот выбрал именно эту карточку?» Пользователь может перестать доверять алгоритму если не видит логику. Нужно объяснять — например, маленькая подпись «📌 повторение» / «🆕 новое» / «🔁 слабая тема».
- **Plan deviation**: что если пользователь хочет учить ровно то, что хочет? Должен быть «free mode» (как сейчас) + «plan mode» — не навязывать.
- **Подмена решения**: если skill map считает пользователя «продвинутым» по теме, а на самом деле тот забыл — упустим важное повторение. Нужны safeguards (например, периодические «проверочные» вопросы по «освоенным» темам).
- **Сложность алгоритма**: priority queue со множеством правил легко становится непрозрачной. Стоит начать с простой версии (60% review + 30% слабые темы + 10% новое) и итерировать.

**Стоимость**:
- Код: значительный (~300-500 строк). Diagnostic flow (новый FSM-state), skill model (новая таблица + сервис обновления), plan generator (алгоритм), UI плана, маркировка items в существующих режимах.
- Контент: высокая. Diagnostic test per subject (5-10 заданий × N предметов) + тегирование всех items темами.
- Алгоритм: требует тюнинг на реальных данных — нельзя заранее «правильно» сделать. Несколько итераций.
- Тесты: pure-функция plan-generator (вход: skill_map + progress, выход: list of items) тестируется юнит-тестом без БД.

**Связь с v0.7**:
- `mcq_progress.correct_count / total_count` → сигнал «знает или нет»
- `flashcard_progress.ease_factor` → «насколько легко даётся»
- `quiz_progress.streak` → «прочно ли освоено»
- `user_subject_stats.last_activity` → «давно ли заходил, не пора ли «разогреться»»
- Всё уже трекается — нужна только надстройка skill model + planner.

**Решение**: **defer**. Возможно v0.8 или v0.9. Сначала собрать реальные данные с прогресса по 4 режимам (трекинг ship'нут в v0.7), понять как реальные пользователи учатся, и только потом строить адаптивную систему. Преждевременно делать «умный» план без понимания паттернов поведения — высокий риск over-engineering. Pre-requisite: достаточная база контента (минимум 30-50 items per subject с тегами тем) — без неё планировать просто нечего.

## Sprint-режим: 14-дневный план под экзамен с checkpoint-тестом (2026-05-18)

**Идея**: альтернативный режим к плану выше — не «бесконечный adaptive» (marathon-style), а **«спринт-подготовка к конкретному экзамену»**: входной тест → план на 14 дней → checkpoint-тест → новый план на следующие 14 дней → итог. Подходит студенту с дедлайном «через 3-4 недели зачёт по ОПМ».

**Зачем (отличие от marathon-варианта выше)**:
- Mental model студента: «у меня экзамен 5 июня — что учить?» — не «учить ровно столько, сколько нужно навыку». Sprint фитит именно это.
- Конкретный артефакт: пользователь видит **14-дневный календарь** заданий — это снимает «когнитивный налог выбора»; ощущение контроля.
- Checkpoint каждые 2 недели — естественная точка переоценки, без перманентного дрейфа skill_map'а.
- Принцип «пропущенный день не сдвигает план» — антипаттерн guilt spiral'а Duolingo; не наказываем дополнительно.

**Подход (черновой)**:
- **Diagnostic test — из учебников** (не LLM, не самописное): 5-10 вопросов из готовых пособий по предмету, привязанные к темам. Минимизирует authoring burden. Минус: тесты не дизайнились под diagnostic, могут плохо различать уровни.
- **Skill — binary** (знаю / не знаю), а не 0-3 как в marathon-варианте. Учебниковые тесты дают мало сигнала для градации; упрощение делает планировщик понятным.
- **БЕЗ target grade** (3/4/5): исходный epic предполагал параметр; убрали, т.к. требовал бы второй слой metadata (`min_grade` per item) — content burden ×2. Приоритезация только по skill_map + topic order + накопленный SRS-прогресс.
- **План на 14 дней**: pre-computed, fixed (не двигается на missed day). Каждый день — список items (карточки/MCQ/задачи/ситуац. термины), нацеленный на:
  1. Слабые темы (skill=0) → необходимый минимум для прохождения предмета;
  2. Повторение освоенного через SRS (overdue карточки/термины);
  3. Mix режимов чтобы избежать монотонии.
- **Время в день** — пользовательский параметр (15/30/45/60+ мин) при создании плана; объём items в день подбирается через грубые оценки (карточка ~2мин, MCQ ~1мин, задача ~5мин).
- **Checkpoint-тест через 14 дней**: новые вопросы из того же банка → пересчёт skill_map → новый план на дни 15-28.
- **«🔁 Сменить план»** кнопка (см. ниже про placement): пользователь может **в любой момент** триггернуть re-test и пересоздание плана — это разрешает гэп discrete adaptation. Если пользователь чувствует что план перестал отражать реальность (быстро прокачался / непонятно), может прервать цикл.

**Где разместить кнопку «🔁 Сменить план»** — *открытый вопрос*:
- (a) В профиле, рядом с `⚙️ Настройки` — но профиль глобальный, а план per-subject; не очень фитит.
- (b) В меню учёбы внутри предмета (контекстная кнопка) — рядом с `📋 Сегодняшний план`. **Моя рекомендация** — наиболее естественно, видна когда нужна.
- (c) В FAQ-блоке (внутри ответа на вопрос «как изменить план?») — informational, не actionable. Скорее всего хуже всех.

Финально решить — на этапе реализации.

**Архитектура**:
- Таблица `user_skill_map(user_id, subject_id, topic, skill INTEGER 0|1, last_updated)` — binary skill.
- Таблица `user_active_plan(user_id, subject_id, plan_json TEXT, created_at, expires_at)` — pre-computed plan на 14 дней; `plan_json` содержит массив дней с items.
- Поле `topics: [...]` в JSON-формате существующих файлов контента (`flashcards.txt` расширяется до 3-полевого формата `term ‖ definition ‖ topics`; MCQ — добавляется поле; tasks — JSON уже есть).
- Диагностические тесты — отдельная папка `study_materials/<subject>/diagnostic/<test_id>.json` с массивом вопросов + правильные ответы + topic tags.
- Plan generator — чистая функция в `services.py`, тестируется без БД.

**Риски** (помимо общих рисков adaptive-плана из marathon-варианта):
- **Учебниковые тесты ≠ хорошие diagnostic-тесты.** Они проверяют «выучил параграф», а не дискриминируют уровень владения темой. Возможно skill_map будет шумным — лечится только эмпирически на реальных юзерах.
- **«Topics» в учебниковых тестах часто implicit.** Учебник делит по главам/параграфам, но не явно «тема: X». Привязка вопрос→тема — ручная работа, на которую нужен предметный эксперт. Чтобы упростить: можно использовать «параграф» как proxy для «темы» для MVP.
- **Topic tagging существующего контента (ОПМ section-i etc.)** — full pass через ~25 терминов × 4 раздела ОПМ ≈ 100 items. Один раз, потом support'ить по мере роста.
- **Pre-computed plan устаревает за 14 дней.** Если пользователь прошёл за 3 дня — план показывает дни 4-14 «пусто». Сейчас решается кнопкой «Сменить план», но это не автомат.
- **Pre-existing pet UI conflicts**: «📋 Сегодняшний план» — ещё одна кнопка в меню предмета; UI начинает плотнеть. Возможно нужен «sticky» plan-mode банер вместо отдельной кнопки.

**Стоимость**:
- Код: ~400 LoC. Меньше чем у marathon-варианта (~500 LoC) за счёт упрощений (binary skill, no target grade, pre-computed plan вместо continuous picker).
- Контент: средняя. **Главная работа** — diagnostic test'ы из учебников + topic-тегирование. Для одного предмета (ОПМ) — 2-3 часа. Для каждого следующего — столько же.
- Тесты: plan generator pure-функция → ~30 unit-тестов. Skill_map update → ~10 тестов. Plan rendering → smoke + manual.

**Отношение к marathon-варианту (предыдущая запись)**:
- **Не взаимоисключающие.** Можно ship'нуть **общую инфраструктуру** (skill_map таблица + topics в контенте + diagnostic test infrastructure) и предложить **выбор режима** при первом входе в предмет:
  - 🏃 **Marathon** (continuous adaptive, без deadline'а) — для долгосрочного skill-building (English).
  - 🎯 **Sprint к экзамену** (14-day pre-computed plan, текущая запись) — для подготовки к зачёту/экзамену.
- Marathon и Sprint используют **один и тот же** skill_map и topic-теги — экономия content burden.
- Если выбирать **только один**: Sprint лучше для текущего основного use-case (студенты, экзамены, дедлайны). Marathon — за рамки v0.8/v0.9.

**Решение**: **defer до v0.9** (после v0.8, который содержит #16 питомца + дальнейший контент). Pre-requisites:
1. Минимум 1 предмет полностью укомплектован контентом (ОПМ Разделы II-IV из TODO #1).
2. Topic-тегирование всего ОПМ-контента.
3. Один полноценный diagnostic-тест из учебника (10 вопросов, привязки к темам).
4. Хотя бы 30 дней живых данных в `events` table — чтобы понимать паттерны use'а.

После этих 4 prerequisites — Sprint можно ship'нуть за **~1-2 рабочих дня** кода.
