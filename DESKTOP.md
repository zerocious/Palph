**Статус:** design accepted, реализация не начата. Решения из §1 приняты
2026-09-05. Этот файл — source-of-truth по десктопу и синхронизации, как

## 1. Принятые решения

| Развилка | Решение |
|---|---|
| **Данные** | **Local-first + синхронизация.** У приложения своя SQLite той же схемы; работает офлайн; синк с сервером через журнал событий |
| **Стек UI** | **PySide6 (Qt6) + QML.** Тот же Python, что и весь проект; LGPL |
| **Связка аккаунта** | Pairing по одноразовому deep-link коду `t.me/<bot>?start=pair_<nonce>`, device token в Windows Credential Manager |
| **Объём v1** | **Полная замена боту за ПК**: профиль, таймер, питомец на рабочем столе, флэш-карты, MCQ, задачи, подготовка |

> **Зафиксировано для истории.** При выборе рекомендовался тонкий клиент
> поверх серверного API — он снимает проблему конфликтов целиком. Выбран
> local-first: офлайн важнее. Поэтому §4 (модель синхронизации) — не
> деталь реализации, а фундамент: **если конфликты не решены строго,
> у пользователя разъезжаются монеты, стрик и интервалы SM-2.**

## 2. Что переиспользуется без изменений

Проверено по коду:

```
bot.py (8057 строк, aiogram)  ─┐
plan_handlers.py (791)         ├─→ services.py (2858) ─→ repository.py (2373) ─→ SQLite
tasks.py (планировщик, 147)   ─┘        ↑                      ↑
                                  единственная связь      чистый aiosqlite,
                                  с aiogram — импорт      ноль зависимостей
                                  трёх exceptions         от фреймворка
```

- **`repository.py`** — 15 репозиториев, конструктор принимает
  `aiosqlite.Connection`. UI-агностичен на 100%. 59 мутирующих методов
  (важно для §4.7).
- **`services.py`** — сервисы принимают **опциональный** `bot=None`
  (см. `StudyService.__init__`): без Telegram просто пропускается отправка
  уведомлений. То есть домен уже умеет работать вне бота.
- **Чистые функции**: `sm2_update`, `derive_emotion`, `get_pet_time_period`,
  `render_pet`, `streak_multiplier`, `freeze_cost`, `piecewise_time_pts`,
  `user_calendar_keys`. Детерминированы → критично для реплея (§4.3).
- **`i18n.py` + `locales/{ru,en}.json`** — интерфейс сразу двуязычный.
- **`assets/pet/`** — ~500 PNG (эмоция × цвет × аксессуар) + подпапки
  времени суток + GIF.
- **`study_materials/`** — 102 JSON-файла контента.
- **`db.py`** — схема; `resolve_env_path` читает `DB_PATH` из env, поэтому
  десктопу достаточно выставить `DB_PATH=%LOCALAPPDATA%\Palph\palph.db`
  **до** импорта `db`, и схема разворачивается локально без правок.

**Ключевое следствие выбора «local-first + Python»:** десктоп не ходит в
сеть за бизнес-логикой. Он импортирует `services` и `repository`
и гоняет их на локальной БД. Переписывается **только** слой хендлеров
(8057 строк `bot.py` → QML-экраны), домен не дублируется. Именно поэтому
«полная замена боту» в v1 реалистична.

### 2.1 Развязка домена и aiogram (сделано)

Чтобы `import services` не тянул в оффлайн-клиент aiogram + pydantic +
magic-filter (~30 МБ и странная зависимость), убраны две связки:

1. **`services.py`** импортировал `TelegramForbiddenError`,
   `TelegramRetryAfter`, `TelegramBadRequest` на уровне модуля. Импорт
   обёрнут в `try/except ModuleNotFoundError` с заглушками. При
   установленном aiogram ловятся настоящие классы — поведение не меняется
   ни на байт; без aiogram заглушки недостижимы, потому что все три
   упоминаются только на путях отправки в Telegram, а те выполняются лишь
   при `bot is not None`.
2. **`locale_bot.py`** (заявлен в докстринге как «хелперы локализации для
   bot.py **и** services.py», реально тянется в `services` через
   `file_upload_security`) импортировал `aiogram.types.BotCommand` ради
   одной функции `commands_for_locale`, которую вызывает только бот при
   старте (`setMyCommands`). Импорт перенесён внутрь функции.

Обе связки закрыты тестом `tests/test_domain_without_aiogram.py`: он
запускает subprocess с блокировкой импорта aiogram и проверяет, что домен
импортируется, чистые функции считают то же самое, а при наличии aiogram
используются настоящие классы исключений, а не заглушки. Вторую связку
нашёл именно этот тест — глазами она не видна, она в третьем звене цепочки
импортов.

**Проверено вживую** (aiogram заблокирован, `DB_PATH` — временный файл):
`init_db` → `create_user` → `StudyService.complete_session(25 мин)` с
`bot=None` отрабатывает целиком — 25 базовых монет + 25 бонусных, ачивка
`first_session`, 25 XP питомцу и level-up до 2-го уровня. То есть весь
геймплейный контур уже работает офлайн, без единой строки нового кода.

## 3. Целевая архитектура

```
┌─ ПК пользователя ───────────────────────────┐        ┌─ сервер (bothost) ──────────────┐
│                                             │        │                                 │
│  QML-экраны + трей + окно питомца           │        │  bot.py (aiogram) ── Telegram   │
│         ↓                                   │        │        ↓                        │
│  services.py + repository.py  ← тот же код →│        │  services.py + repository.py    │
│         ↓                                   │        │        ↓                        │
│  локальная SQLite  ←──── sync_client.py ────┼─HTTPS──┼→ sync_api.py ──→ серверная SQLite│
│  (%LOCALAPPDATA%)         outbox/cursor     │        │   журнал sync_log               │
└─────────────────────────────────────────────┘        └─────────────────────────────────┘
```

Обе стороны — равноправные реплики одной пользовательской БД. Сервер
дополнительно играет роль **арбитра**: он держит журнал в каноническом
порядке и разрешает случаи, которые локально не разрешимы (§4.5).

## 4. Модель синхронизации

### 4.1 Принцип: единица обмена — событие, а не строка

Синхронизировать строки таблиц напрямую нельзя: `total_coins = 340` с двух
устройств — это два несовместимых утверждения, и любой выбор теряет данные.
Синхронизируются **факты** («сессия 25 минут завершена в 14:03»), а
состояние из них выводится. Факты по своей природе не конфликтуют — они
просто все произошли.

У проекта уже есть привычка к этому: таблица `events` и `EventRepository`
пишут аналитический журнал. Синк-журнал — его строгий брат: те же идеи,
но с гарантией доставки и порядка.

### 4.2 Тотальный порядок

Каждое событие несёт `(occurred_at, lamport, device_id)`:

- `occurred_at` — UTC ISO-8601 по часам устройства;
- `lamport` — монотонный счётчик устройства (переживает перевод часов
  назад и совпадение таймстампов до миллисекунды);
- `device_id` — uuid4 устройства, финальный детерминированный тай-брейк.

Сортировка по этой тройке даёт **одинаковый порядок на всех репликах**.
Это и есть условие того, что реплей сходится.

Часы устройства могут врать. Сервер при приёме проверяет `occurred_at` на
разумность (±24 ч от серверного времени); выход за окно логируется и
таймстамп клампится, событие не теряется.

### 4.3 Классификация состояния — четыре класса, четыре правила

Все 28 таблиц из `db.py` разнесены по классам. Это ядро спеки: **новая
таблица обязана получить класс до того, как попадёт в схему.**

| Класс | Правило слияния | Таблицы |
|---|---|---|
| **Append-only** | Объединение по uuid. Конфликтов не бывает | `study_sessions`, `events`, `user_flashcards`, `user_tasks`, `user_pet_inventory`, `user_tips_seen`, `streak_freezes` |
| **Derived** (свёртка) | Пересчёт реплеем событий в тотальном порядке | `users.total_coins/total_sessions/current_streak/last_session/has_studied_today`, `user_pet.level/xp`, `flashcard_progress` (SM-2), `quiz_progress`, `mcq_progress`, `task_progress`, `user_subject_stats.visits`, `daily_score_counters`, `weekly_scores`, `user_achievements`, `user_tips_stats.total_views` |
| **Register** (LWW) | Побеждает большее `(occurred_at, lamport, device_id)` | `users.timezone`, все поля `notification_settings`, `user_pet.name/color/accessory`, `user_skill_map`, `user_active_plan.plan_json` (целиком, как один документ), `user_plan_meta`, `user_tips_stats.tip_of_day_*` |
| **Server-only** | Локально read-only кэш; менять можно только онлайн | `friend_requests`, `friendships`, `friend_invite_tokens`, `weekly_badges`, `admins`, ранги лидерборда |
| **Local-only** | Не синкается вообще | `fsm_storage` (у десктопа своё UI-состояние) |

Почему Derived сходится: все свёртки — **чистые детерминированные
функции** от упорядоченной последовательности событий. `sm2_update` при
одинаковом входе даёт одинаковый выход; стрик — функция от множества дат
активности (объединение множеств коммутативно); недельные очки — сумма.
Ни в одной из них нет обращения к «текущему времени» в момент свёртки.

### 4.4 Монеты как ledger — обязательная миграция

`users.total_coins` — скаляр, и это единственное место, где схема прямо
мешает синхронизации: два устройства, начислившие по 25 монет офлайн,
дадут либо 25, либо 25, но не 50, при любом правиле слияния строк.

Поэтому баланс становится **производным от журнала списаний/начислений**:

```sql
CREATE TABLE IF NOT EXISTS coin_ledger (
    event_uuid  TEXT PRIMARY KEY,      -- = uuid события, идемпотентность
    user_id     INTEGER NOT NULL,
    delta       INTEGER NOT NULL,      -- +25 сессия, -120 покупка
    reason      TEXT NOT NULL,         -- session|mcq|task|purchase|weekly_reward|freeze|legacy
    occurred_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_coin_ledger_user ON coin_ledger(user_id, occurred_at);
```

`users.total_coins` остаётся, но становится **кэшем** `SUM(delta)`.
Сложение коммутативно → порядок применения не важен, потерять начисление
невозможно.

**Миграция существующих данных:** для каждого пользователя одна строка
`reason='legacy'`, `delta = users.total_coins` на момент миграции,
`occurred_at` = время миграции. Дальше — только дельты. Прогоняется в
`db.py` как обычная idempotent-миграция, с проверкой инварианта
`SUM(delta) == total_coins` по всем пользователям до и после.

### 4.5 Двойное списание — единственный настоящий конфликт

Ledger решает начисления, но не траты. Сценарий: 150 монет, оба устройства
офлайн, на каждом куплен аксессуар за 120. Локально обе покупки валидны, в
сумме баланс уходит в −90.

Правило: **сервер — арбитр по тратам.**

1. Сервер реплеит события в тотальном порядке, ведя текущий баланс.
2. Первая покупка проходит, вторая уводит баланс ниже нуля → отклоняется.
3. Сервер пишет в журнал компенсирующее событие `purchase.rejected`
   (ссылка на `event_uuid` отклонённой покупки).
4. Устройство, получив его, откатывает свою локальную покупку и **явно**
   говорит пользователю: «Покупка "корона" отменена — монет не хватило,
   их потратило другое устройство. Баланс: 30 🪙».

Молчаливый откат недопустим: пропавший из инвентаря предмет выглядит как
баг. Отклонение — редкий случай (нужно тратить офлайн с двух устройств
одновременно), но обработать его надо честно.

**Тот же арбитраж применяется к:** заморозке стрика (`streak_freezes`,
тоже трата), покупкам в магазине питомца, и любой будущей механике со
списанием.

### 4.6 Схема синхронизации

**На устройстве** (в дополнение к обычной схеме `db.py`):

```sql
-- Исходящие: локальные события, ещё не подтверждённые сервером
CREATE TABLE IF NOT EXISTS sync_outbox (
    event_uuid  TEXT PRIMARY KEY,
    user_id     INTEGER NOT NULL,
    kind        TEXT NOT NULL,        -- см. §4.7
    payload     TEXT NOT NULL,        -- JSON
    occurred_at TEXT NOT NULL,
    lamport     INTEGER NOT NULL,
    acked_at    TEXT                  -- NULL пока сервер не подтвердил
);

-- Применённые события (и свои, и чужие) — защита от повторов
CREATE TABLE IF NOT EXISTS sync_applied (
    event_uuid TEXT PRIMARY KEY,
    applied_at TEXT NOT NULL
);

-- Курсор пула, счётчик Лампорта, device_id, время последнего синка
CREATE TABLE IF NOT EXISTS sync_state (key TEXT PRIMARY KEY, value TEXT NOT NULL);
```

**На сервере:**

```sql
CREATE TABLE IF NOT EXISTS sync_log (
    seq         INTEGER PRIMARY KEY AUTOINCREMENT,   -- курсор для pull
    user_id     INTEGER NOT NULL,
    event_uuid  TEXT NOT NULL UNIQUE,                -- идемпотентность push
    device_id   TEXT,                                -- NULL = событие бота
    kind        TEXT NOT NULL,
    payload     TEXT NOT NULL,
    occurred_at TEXT NOT NULL,
    lamport     INTEGER NOT NULL,
    applied_at  TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_sync_log_user_seq ON sync_log(user_id, seq);

CREATE TABLE IF NOT EXISTS devices (
    device_id    TEXT PRIMARY KEY,
    user_id      INTEGER NOT NULL,
    token_hash   TEXT NOT NULL,        -- sha256, plaintext не храним
    device_name  TEXT,
    created_at   TEXT NOT NULL,
    last_seen_at TEXT,
    revoked_at   TEXT
);

CREATE TABLE IF NOT EXISTS pair_codes (
    nonce      TEXT PRIMARY KEY,
    device_id  TEXT NOT NULL,
    user_id    INTEGER,               -- NULL пока не подтверждено в боте
    created_at TEXT NOT NULL,
    expires_at TEXT NOT NULL,         -- TTL 10 минут
    used_at    TEXT
);
```

Прецедент для pairing уже есть — `friend_invite_tokens` и `/share_friend`
делают ровно тот же трюк с deep-link'ами и TTL.

### 4.7 Протокол

```
POST /api/v1/sync/push   {events: [...]}          → {acked: [uuid], rejected: [{uuid, reason}]}
GET  /api/v1/sync/pull?since=<seq>&limit=500      → {events: [...], next_seq, has_more}
POST /api/v1/pair/start  {device_id, device_name} → {nonce, deep_link, expires_at}
GET  /api/v1/pair/poll?nonce=                     → 202 pending | 200 {token, user_id}
POST /api/v1/devices/revoke {device_id}
```

Цикл клиента: **push → pull → пересчёт свёрток → отрисовка**. Запускается
при старте, по таймеру (~60 с онлайн), при возврате сети и после каждого
значимого действия. Всё в фоновом потоке; UI никогда не ждёт сеть.

**Виды событий** (~25–30 на все фазы; в `repository.py` 59 мутирующих
методов, из них server-only и производные-пересчёты событий не требуют):

```
session.started / session.finished / session.aborted
flashcard.reviewed          {card_hash, quality}
mcq.answered                {question_hash, correct}
task.attempted              {task_id, succeeded, attempts_used}
quiz.answered               {term_hash, is_correct}
subject.visited             {subject_id}
coins.granted               {delta, reason}
purchase.made               {item_type, item_value, price}
purchase.rejected           {ref_uuid, reason}         ← только сервер
pet.customized              {color?, accessory?}       ← register
pet.renamed                 {name}                     ← register
streak.freeze_purchased / streak.freeze_consumed
settings.changed            {field, value}             ← register
timezone.changed / locale.changed                      ← register
flashcard.created / flashcard.deleted
usertask.created / usertask.deleted
plan.updated                {subject_id, plan_json}    ← register, документ целиком
tip.seen                    {tip_id}
```

**Бот тоже обязан эмитить события.** Сегодня хендлеры пишут через
репозитории напрямую — при этом сервер не узнает, что изменилось, и
десктоп не получит апдейт. Поэтому вводится `sync.py` с функцией
`emit(db, user_id, kind, payload)`, и её вызовы расставляются в сервисах
(не в 59 методах репозиториев, а в ~25 точках сервисного слоя, где
операции уже сведены: `StudyService.finish`, `LeaderboardService.grant_*`,
`PetRepository.purchase`, смена настроек и т.д.).

**Инвариант, который проверяет тест:** для любого набора событий
`replay(shuffle(events))` даёт то же состояние, что `replay(events)`,
и совпадает с состоянием сервера. Это property-based тест, а не пример.

### 4.8 Первый синк и восстановление

- **Первый запуск после pairing:** сервер отдаёт снапшот (текущее
  состояние + `seq`), а не весь журнал с начала времён. Журнал режется
  ретеншном (90 дней), снапшот — точка отсчёта.
- **Устройство отстало сильнее ретеншна:** сервер отвечает
  `410 snapshot_required`, клиент делает полную перезаливку.
- **Расхождение свёрток:** клиент раз в сутки шлёт контрольные суммы
  (баланс, стрик, число сессий); при расхождении с сервером —
  принудительный ресинк со снапшота и запись в лог. Это страховка от
  ошибок в правилах слияния, которые в такой системе неизбежно найдутся.

## 5. Границы офлайна

Работает офлайн: таймер, питомец, флэш-карты, MCQ, задачи, подготовка,
профиль, покупки (с риском арбитража по §4.5), настройки, планы.

**Требует сети** и в офлайне показывается как read-only кэш с явной
плашкой «данные на 14:32»:

- лидерборд (ранг зависит от всех пользователей);
- друзья: заявки, принятие, удаление (действие затрагивает второго
  человека — локально его согласие не подделать);
- weekly rollover и награды (считает сервер по UTC-якорю);
- админ-функции (в десктопе их нет вообще).

## 6. Время и стрики

`current_streak` и weekly rollover — UTC-якорные (см. LEADERBOARD.md).
Правило: **десктоп не изобретает даты сам.** Он вычисляет локальную дату
через ту же `user_calendar_keys` от `users.timezone`, а не от часового
пояса Windows: иначе поездка в другой часовой пояс порвёт стрик. Часовой
пояс — register-поле, меняется явно в настройках и синкается.

Weekly rollover считает **только сервер**. Десктоп его результат
показывает, но не воспроизводит: иначе две реплики независимо начислят
недельные награды.

```
│   │   ├── pet_window.py     # прозрачное always-on-top окно питомца
│   │   ├── timer.py          # помидор: виджет, трей, тосты
│   │   ├── ui/*.qml
│   │   └── resources/        # locales/ + assets/pet/ (копируются при сборке)
│   ├── requirements.txt      # PySide6, httpx, keyring, plyer
│   ├── palph.spec            # PyInstaller (--onedir: старт быстрее --onefile)
│   ├── installer.iss         # Inno Setup → Palph-Setup-x.y.z.exe
│   └── tests/
└── tests/                    # существующие 787, не трогаем
```

- **aiohttp** — уже транзитивная зависимость aiogram, для `sync_api.py`
  новых пакетов на сервере не нужно.
- `sync_api.py` поднимается **в том же процессе, что бот** — тогда у
  серверной SQLite один владелец и WAL решает всё. Отдельный процесс
  потребовал бы Postgres.
- CI: job на `windows-latest`, артефакт — установщик; релизы через GitHub
  Releases (там же канал автообновления).
- Подпись кода: без EV-сертификата (~$200–400/год) SmartScreen ругается на
  каждой установке. Для учебного проекта допустимо; решить до публичной
  раздачи.

## 9. Риски

1. **Сходимость реплик — главный риск проекта.** Митигация: фаза 0 первой,
   property-based тест перестановок, суточные контрольные суммы (§4.8),
   принудительный ресинк при расхождении.
2. **Двойные уведомления.** `devices.last_seen_at` как presence-флаг: ПК
   онлайн → нативный тост, `ReminderService` пропускает Telegram (или
   наоборот, по настройке). Зафиксировать до фазы 2.
3. **Хостинг API.** Отдаёт ли тариф bothost.ru публичный порт и домен?
   Блокер фазы 1 — проверить первым. При отказе: VPS либо туннель.
4. **Миграция `coin_ledger` на живых данных.** Только с бэкапом
   (`BackupService.force_backup()` уже есть) и проверкой инварианта
   `SUM(delta) == total_coins` до и после.
5. **Размер дистрибутива.** `assets/pet/default.png` — 2 МБ, всего ~500
   PNG. Прогнать через `scripts/build_pet_assets.py` и ужать, иначе
   установщик распухнет.
6. **Приватность.** Трекинг активного окна (фаза 5) — сбор чувствительных
   данных: строго opt-in, только локально, обязательный апдейт
   [PRIVACY.md](PRIVACY.md) / [PRIVACY.ru.md](PRIVACY.ru.md). Локальная БД
   на ПК — тоже персональные данные, нужен раздел про них.
7. **Кража device token.** Токен в Credential Manager, а не в файле рядом с
   exe; отзыв устройства из бота; при `revoked_at` сервер отвергает push.
